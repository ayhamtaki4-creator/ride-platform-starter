# حجوزات الضيوف وتفعيل الحسابات

## الواجهة العامة

- `POST /api/bookings/guest`: إنشاء حجز عام بدون تسجيل دخول.
- `POST /api/bookings/guest-with-ticket`: نموذج multipart بحقل `booking` يحوي بيانات JSON وحقل `file` لتذكرة PDF/صورة (حتى 10MB).
- كلا المسارين يستخدمان معرف طلب عشوائي `clientRequestId` لمنع تكرار الحجوزات عند إعادة الإرسال.
- يعرض المتصفح رقم الحجز فقط في صفحة النجاح. لا يُسمح بالاطلاع على سجل رحلة عبر رقم الحجز العام.

## سلوك الحساب

- رقم جديد: ينشأ حساب `PASSENGER` معلق ومؤقت؛ لا يمكن تسجيل الدخول حتى إثبات ملكية الهاتف.
- رقم مسجل: يبقى الحجز `passengerId = NULL` ولا تتغير كلمة مرور المستخدم، حتى التحقق من الرقم.
- رقم مؤكد: يتم ربط الحجوزات غير المرتبطة التي لها نفس الرقم الدولي الموحّد بالحساب.
- حساب جديد مُفعّل: تتولد كلمة مرور عشوائية تُعرض للعميل الذي أكمل OTP عبر اتصال HTTPS مرة واحدة، ويُطلب تغييرها عند أول دخول.
- إشعار Telegram يذكر نوع الحجز وحالة إنشاء الحساب **دون** كلمة المرور أو رمز التحقق.

## إعداد WhatsApp OTP

أضف في خدمة API على Render:

```env
WHATSAPP_ENABLED=true
WHATSAPP_ACCESS_TOKEN=...
WHATSAPP_PHONE_NUMBER_ID=...
WHATSAPP_GRAPH_API_VERSION=v25.0
WHATSAPP_OTP_TEMPLATE=tareeq_phone_verification
WHATSAPP_OTP_LANGUAGE=ar
```

يجب اعتماد قالب من Meta ضمن فئة **AUTHENTICATION** مع زر **COPY_CODE**. يرسل النظام رمزًا سداسيًا في جسم القالب وزر النسخ، وينتهي التحقق بعد عشر دقائق أو خمس محاولات خاطئة. يُقيّد طلب الرمز حسب عنوان IP والرقم، وتمنع الاستجابة كشف وجود الحساب.

إذا لم يتوفر القالب أو الاتصال بمزود WhatsApp، تظهر رسالة بأن تفعيل الحساب غير متاح بدل إصدار كلمة مرور أو السماح بالدخول غير الموثق. **لا تضبط `WHATSAPP_ENABLED=true` دون بيانات الاعتماد والقالب الموافق عليه.**

## تخزين التذاكر

تُرفق تذكرة الضيف بالرحلة كملف **PRIVATE**، ويملكها حساب خدمة معلّق ومخصص للتخزين (لا يملك أدوارًا أو جلسات دخول). لا يمكن طلب الملف مباشرة دون صلاحيات. يتطلب نشر Render استخدام تخزين دائم/R2 عند تفعيل `MEDIA_REQUIRE_R2`.

إذا أُنشئ الحجز وتعذر رفع التذكرة، تبقى بيانات المسودة في المتصفح ويمكن إعادة إرسال الملف باستخدام نفس `clientRequestId` دون إنشاء حجز ثان.

## التحقق قبل الدمج

1. نسخة احتياطية من PostgreSQL قبل تشغيل `prisma migrate deploy`.
2. تشغيل Migrations على بيئة اختبار **قبل** تشغيل إصدار API الجديد، إذ تغيرت علاقة `Trip.passengerId` لتصبح اختيارية.
3. تشغيل `pnpm db:generate`, `pnpm typecheck`, `pnpm build`.
4. اختبار رقم جديد، رقم موجود، محاولة إعادة إرسال الحجز، رفع PDF وصورة، تدفق حساب جديد، تأكيد OTP، تغيير كلمة المرور، وعرض بيانات السائق والإدارة وTelegram.
5. اختبار استعادة الحساب عند عدم توفر WhatsApp، وتجنب ربط حسابات دون التحقق.
6. نشر نسخة API ثم بوابة Cloudflare فقط بعد نجاح التجربة؛ المسار القديم للمسجلين يبقى مدعومًا.

> الأرقام السابقة قد تكون مكتوبة بصيغ مختلفة؛ معالجة الحجوزات الجديدة تستخدم صيغة `+<country><number>`. تحقق من توحيد أرقام المستخدمين القديمة قبل تفعيل الربط الجماعي.
